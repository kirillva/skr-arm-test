# План автотестов для АРМ (dev-стенд)

> **Статус: v1 реализована и стабилизирована (01.11.2026).**
> Проверочный прогон `--repeat-each=3 --retries=0`: 66 passed / 0 failed / 3 skipped (known-bug).
> Следующий этап — функциональные тесты (вне рамок v1).

**Объект:** https://skr.it-serv.ru/arm/dev/#/auth (React SPA, hash-роутинг)
**Инструмент:** Playwright + TypeScript (E2E + API в одном раннере)
**Версия 1 (этот план):** авторизация, RBAC-состав интерфейса, API-контракты.
**Вне рамок v1:** функциональные сценарии (таблицы, фильтры, CRUD, отчёты, загрузки файлов), браузеры кроме Chromium, производительность, доступность.

## Данные и окружение

- Логин основной учётки: `manager` / `manager0` (профиль `administrator`, макс. доступ).
- Авторизация API: заголовок `rpc-authorization: Token base64(login:password)`; RPC `POST https://skr-dev.it-serv.ru/dev/rpc/{core,dbo,mrkt}`.
- Сессия не хранится в localStorage/cookies → `storageState` неприменим, логин в фикстурах через UI.
- Маскировка: кнопка «Замаскироваться» в блоке «Авторизованные устройства» на `#/admin/userdetail?id=<id>&profile=<profile>`; выход из маски завершает сессию полностью.

## Этап 0. Каркас проекта

- `npm init`, зависимости: `@playwright/test`, `typescript`, `dotenv`.
- Структура:
  ```
  ArmTest/
  ├── tests/
  │   ├── auth/          # UI-тесты авторизации
  │   ├── api/           # контракты API
  │   └── rbac/          # состав интерфейса по ролям
  ├── pages/             # Page Object'ы
  ├── fixtures/          # фикстуры (логин, маскировка)
  ├── .env / .env.example
  ├── playwright.config.ts
  └── PLAN.md
  ```
- `playwright.config.ts`: baseURL, Chromium, workers=1 (dev-стенд, сессия одна), retries=1, отчёты html+list, trace/screenshot/video — только при падении.
- `.env`: BASE_URL, API_URL, MAIN_LOGIN, MAIN_PASSWORD, ROLE_<PROFILE>_LOGIN/ID. В репозиторий — только `.env.example`.

## Этап 1. Инфраструктура

- `LoginPage` (PO): поля Логин/Пароль, кнопки «Войти в систему», «Забыли пароль?», переключатель видимости пароля, диалог ошибки; локаторы — по роли/имени (`getByRole`), без data-testid их у приложения нет.
- Фикстура `loginAsManager`: переход на `#/auth`, ввод из `.env`, ожидание редиректа на `#/dispatching/map`.
- Фикстура `impersonate(profile)`: от имени manager → `#/admin/userdetail?id&profile` → развернуть «Авторизованные устройства» → клик «Замаскироваться» → подтвердить смену пользователя в шапке; teardown: «Выход» → повторный логин manager.
- API-хелпер `rpc(service, body)`: POST с заголовком Token; используется для позитивных/негативных API-тестов (UI для этих целей не нужен).

## Этап 2. Тесты авторизации (`tests/auth`, тег @auth)

1. Страница `#/auth` открывается: заголовок «Авторизация», поля, кнопки, версии контейнера/АРМ.
2. Пустая форма → под каждым полем «Не заполнено обязательное поле», на `#/auth` остаёмся.
3. Неверные данные → диалог «Сообщение» с текстом «Неверный логин или пароль…», кнопка Ok закрывает диалог, пользователь на `#/auth`.
4. Успешный вход `manager` → редирект на `#/dispatching/map`, в шапке имя `manager`.
5. Кнопка-глазик переключает тип поля пароля (masked ↔ visible).
6. Прямой заход на защищённый URL без сессии (`#/admin/users`) → редирект на `#/auth`.
7. Выход из-под manager → возврат на `#/auth`; повторный прямой заход в раздел снова редиректит.
8. «Забыли пароль?» → зафиксировать фактическое поведение (диалог/переход) как ожидаемое.

## Этап 3. API-контракты (`tests/api`, тег @api)

1. `POST /dev/auth` (multipart UserName/Password) корректные → 200, `meta.success=true`.
2. Неверные → 401, `meta.success=false`, `msg="Пользователь не авторизован."`.
3. Пустые UserName/Password → ожидаемый код/ошибка (зафиксировать факт).
4. `rpc/core of_users` с валидным Token → 200, непустой `records`, есть поля `c_login`, `c_profile_const`.
5. `rpc/core` без заголовка `rpc-authorization` → 401.

## Этап 4. RBAC-состав интерфейса (`tests/rbac`, тег @rbac)

Для каждой маскируемой роли (administrator, manager, manageruser, boss, pco, subpco, repo):
1. **Состав навигации** после маскировки = ожидаемый список секций (таблица выше).
2. **Состав вкладок** в каждой секции = ожидаемый список.
3. **Негативный доступ**: переход по URL раздела, которого-role нет → 404/редирект (напр. `manager` → `#/admin/users`, `repo` → `#/dispatching/map`, `pco` → `#/tu_planning`).

Отдельно:
4. Профиль `user` (Контролёр): после маскировки веб-маршруты отдают 404 — регрессионный «известное ограничение».
5. Профили `market`/`provider`/`brigade`: на странице пользователя нет блока «Авторизованные устройства» (проверка на уровне DOM-состава страницы) — документируем как ограничение механизма маскировки.

## Этап 6. Стабилизация

- Прогон комплекта 3 раза подряд на dev; цель — 0 флаков без правок тестов между прогонами.
- Точечные правки ожиданий (вместо sleep — ожидание состояний/редиректов).

## Риски

- Dev-стенд живой: данные/состав вкладок могут меняться → матрица RBAC вынесена в один конфиг-файл `rbac.matrix.ts`, правка в одном месте.
- Выход из маски убивает сессию → все RBAC-тесты начинают проём с полного логина (учтено в фикстуре, но стоимость ~10–15 с/тест; при большом числе тестов склеим проверки роли в один тест-файл с общим setup).
- Виртуализированные таблицы — не проверяем содержимое строк (это функциональные тесты, вне v1).
- Учётка `manager` — единственная; параллельные прогоны из двух мест конфликтуют (workers=1, одна сессия).

## Наблюдения по стенду (01.11.2026, АРМ 1.1.290)

- **RBAC-гэп**: у роли `boss` раздел «ТУ подрядчиков» скрыт в навигации, но маршрут `#/tu_planning`
  открывается напрямую по URL (страница «Формирование плана для подрядчиков» с таблицей и кнопкой
  «Добавить в план»). Для `administrator` тот же маршрут закрыт (404). Зафиксирован тестом-характеризацией
  `tests/rbac/known-issues.spec.ts` (`@known-bug`, `test.fixme` до фикса на стенде).
- Контракты API: успешный `POST /auth` возвращает `{ token, user, projectId }` (без `meta`);
  ошибки — объект `{ meta: {...} }`, успешные RPC — массив `[{ meta, result }]`.
- **Gap валидации (dev, 01.11.2026)**: заявку «Запрос оборудования» можно создать со строкой
  оборудования без категории — сервер сохраняет позицию с `c_tags=".."` (клиентский
  `checkProductsError` не сработал). Такая заявка потом не исполняется по CSV (категория не
  сопоставляется). Зафиксировано созданием заявки `01112026-437` (остаётся CREATED на dev).
- **Нестабильность CSV-загрузчика (dev, 01.11.2026, два симптома)**:
  1) загрузка CSV до готовности справочника категорий загрузчика (`of_arm_product_tags`) —
     парсер падает на `productTags=null`, кнопка зависает в загрузке без сообщения;
  2) «молчаливый» пустой результат: парсинг завершается, кнопка активна, но строки не
     заполнены и ошибок нет (formatSendData пустой без видимых причин; не воспроизводится
     стабильно). Кандидат в баг-репорт (нужны сообщения об ошибках и защита от гонки).
     В тестах обработано: ожидание двух ответов `of_arm_product_tags` в `openResolveForm` +
     повторные загрузки до эффекта в `uploadRequestCsvUntil`.
- Флак маскировки: клик «Замаскироваться» в виртуализированной таблице устройств иногда открывает
  диалог «Редактирование» устройства вместо маскировки (обработано ретраем в `impersonate()`).
